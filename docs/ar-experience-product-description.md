# 阊门现场 AR 历史叠景体验产品描述

## 文档用途

本文档用于向 AI、开发者或合作者说明当前项目中计划实现的 AR demo，避免每次重新描述产品设想。它不是纯概念稿，而是基于现有 `loc-ar.html`、Immersal 定位、Three.js 模型锚点和 `arAnchors.js` 配置能力整理出的可实现 demo 描述。

## 一句话概述

这是一个基于手机浏览器运行的阊门现场 AR demo。用户在真实阊门城门和城墙空间中移动，系统通过 Immersal 识别当前位置，并根据识别到的空间内容显示对应的历史叠景：城墙步道上的漂浮介绍牌、不同悬眼中的朝代街景传送窗，以及从垛口向外观看时完全覆盖现实画面的瓮城城墙复原层。

## 当前项目基础

项目已有一个可用的 Web AR 原型入口：

- `loc-ar.html`：AR 体验页入口。
- `src/pages/ArPage.jsx`：相机启动、地图选择、缩放控制、提示栏和 debug 面板。
- `js/ar/arScene.js`：Immersal 定位流程，优先使用 SDK 连续定位，失败后回退到 REST 定时识别。
- `js/ar/arRenderer.js`：Three.js 透明画布渲染，负责把 3D 内容叠加到相机画面上。
- `js/ar/arAnchors.js`：不同 Immersal map ID 对应不同 AR 锚点和模型。
- `loc-ar-editor.html` / `js/ar/arPlacementEditor.js`：锚点摆放工具，可加载点云，调整模型位置、旋转、缩放，并导出新的 `arAnchors.js`。

当前程序已经具备“识别真实空间位置，并在对应地图坐标系中显示 3D 模型”的技术基础。后续 demo 的重点是把单一测试模型扩展为多种历史内容模块。

## 核心体验原则

体验不是固定线性剧情，而是空间识别驱动的非线性 AR。

用户看到什么内容，应由当前识别到的真实空间决定：

- 识别到城墙步道区域：显示排列好的漂浮介绍牌。
- 识别到某个悬眼区域：显示该悬眼对应朝代的 AR 传送窗。
- 识别到垛口区域：触发瓮城城墙复原层，完全覆盖现实画面。

用户可以按现场移动顺序自由探索，不要求严格按照固定流程完成体验。

## 目标设备与运行方式

MVP demo 基于当前网页项目实现，不另做 Unity 或独立 App。

目标运行方式：

1. 用户用手机浏览器打开 `loc-ar.html`。
2. 页面请求相机和方向传感器权限。
3. 系统通过 Immersal 识别当前位置或当前视角对应的 map。
4. Three.js 在相机画面上叠加对应 AR 内容。

## 内容模块

### 1. 城墙步道漂浮介绍牌

当系统识别到城墙步道或城门上方的行走区域时，在真实空间中显示一组预先排列好的漂浮介绍牌。

这些介绍牌不是普通网页说明，而是放置在 AR 空间中的信息节点。用户行走时会自然看到它们按空间顺序展开。

建议内容风格为“短句历史碎片卡”：

- 每张牌包含时期、标题、一句话解释和简单视觉符号。
- 内容应短、轻、可扫读，避免长篇说明。
- 视觉上可参考博物馆导览牌，但更轻盈，适合漂浮在城墙空间中。

示例内容：

- 公元前 514 年：阊门初建，原名破楚门，是苏州古城八门之一。
- 南宋时期：水陆城门并列，阊门成为古城水网与交通的重要节点。
- 明清时期：阊门外商贾云集，街市、河道、码头共同形成繁华商业区。
- 近代转型：战乱、道路和交通方式变化，使阊门空间逐渐进入现代城市格局。

实现上，可以在某个 Immersal map 的坐标系中预先摆放多个信息牌锚点，而不需要复杂路径追踪。

### 2. 悬眼 AR 传送窗

“悬眼”在本 demo 中被定义为 AR 传送窗。

用户将手机镜头对准城墙上的悬眼/观察孔后，悬眼另一侧显示的不是现实场景，而是某一历史时期的阊门外街景复原。不同悬眼对应不同朝代或时期。

根据现场照片和测试反馈，悬眼不是薄平面窗口，而是一个约 20-30cm 厚、接近人头大小的方形石质通道。用户不可能整个人穿过悬眼，但手机可以贴近悬眼入口，甚至伸入几厘米。因此第一版实现不应把它做成普通贴片窗口，而应做成 B 级 portal 遮罩效果：

- 保留真实相机画面中的石质洞壁、阴影、边缘和厚度。
- 只替换洞口尽头外侧看到的现实树木、天空或现代景物。
- 历史街景必须被限制在远端方形开口内，不能漏到洞壁、墙面或洞口外区域。
- 手机距离和角度变化时，真实洞壁由相机画面自然产生透视，历史世界则通过 AR pose 固定在洞口外侧空间中产生视差。
- 洞口边缘可以加入轻微暗边、羽化或遮罩余量，以容忍现场对齐误差。

推荐空间结构：

```text
手机相机
  ↓
真实石壁通道（保留现实相机画面）
  ↓
洞口远端方形开口（portal aperture / stencil / clipping mask）
  ↓
远景历史小世界（低模 3D 建筑 + 背景图）
```

这里的关键不是重建整段墙体，而是让历史世界只出现在真实悬眼尽头的开口后方。真实洞壁本身已经提供了厚度感，AR 主要负责“替换洞外世界”。

计划使用 4 个历史窗口：

1. 南宋《平江图》时期  
   展示水陆城门并列、水网密布、阊门作为城市交通节点的空间格局。

2. 明清商业鼎盛时期  
   展示阊门外街市、商铺、船只、人流、码头与货物流通，强调繁华商业中心形象。

3. 晚清 / 民国转型时期  
   展示战乱后街区变化、近代道路、交通方式转变和传统水运衰落。

4. 当代对比  
   展示今日阊门与历史复原之间的对照，让用户理解哪些空间已经消失、重建或转化。

MVP demo 中，街景复原可以先使用低精度 3D 场景、半景片、剪影、牌匾、船只、人物轮廓等方式表达朝代差异。完整版本再替换为更高精度、经过考据的街景复原模型。

当前确认的内容表现形式为“低模 3D 建筑 + 背景图”：

- 洞口后 2-4 米放少量低模近景元素，例如街道边缘、屋檐、船只、人群剪影或码头结构。
- 洞口后 8-20 米放主要历史街景，例如商铺、河道、城外道路、船队和街市。
- 更远处使用背景图补足天空、远街、远处建筑和整体氛围。
- 用户不需要点击悬眼内容，只需对准观看。
- 已测试的悬眼形态相近，可优先做一个通用方形 portal 模板，再为不同 map 配置位置、大小和朝代内容。

### 3. 垛口瓮城城墙复原层

当用户从垛口向外看时，系统触发瓮城城墙复原层。

这个模块的目标不是精确还原现实遮挡关系，而是让用户在当前位置获得“原本这里曾有完整防御空间”的直观想象。

由于真实深度遮挡在手机 Web AR demo 中不稳定，MVP 采用完全覆盖现实画面的历史复原层：

- 用户对准垛口后，现实画面被大面积瓮城城墙复原模型覆盖。
- 复原层优先保证整体空间感和视觉完整性。
- 不追求与远处现代建筑、树木、车辆等现实物体逐像素深度融合。
- 该设计可以在文档中说明为技术取舍：牺牲深度准确性，换取 demo 的可实现性和历史空间想象力。

## 交互逻辑

AR 内容由识别结果触发，而不是固定顺序触发。

建议触发规则：

- 每个 Immersal map ID 对应一个空间区域或视角。
- 每个空间区域配置一个或多个 AR 内容锚点。
- 当定位结果锁定到某个 map ID 后，只显示该 map 对应内容。
- 如果处于多地图识别模式，需要避免频繁切换，可继续使用当前代码中的地图锁定和确认机制。

推荐内容映射：

| 识别区域 | AR 内容 | 说明 |
| --- | --- | --- |
| 城墙步道 | 漂浮介绍牌组 | 介绍阊门历史背景和游览线索 |
| 悬眼 1 | 南宋传送窗 | 《平江图》时期水陆格局 |
| 悬眼 2 | 明清传送窗 | 商业鼎盛、街市与河运 |
| 悬眼 3 | 晚清 / 民国传送窗 | 战乱、道路和近代转型 |
| 悬眼 4 | 当代对比传送窗 | 现实与历史复原对照 |
| 垛口 | 瓮城城墙覆盖层 | 完全覆盖现实画面的空间复原 |

如果现场只有 3 个可稳定识别的悬眼，也可以将“当代对比”并入漂浮介绍牌或垛口模块。

## MVP 实现范围

MVP 必须是可运行 demo，而不是只停留在概念描述。

最低可实现目标：

1. 继续使用 `loc-ar.html` 作为体验入口。
2. 继续使用 Immersal map ID 识别空间位置。
3. 在 `arAnchors.js` 中为不同 map 配置不同内容锚点。
4. 将当前单一 GLB 模型扩展为多种内容类型：
   - 3D 漂浮信息牌。
   - 悬眼内的历史窗口或半景片。
   - 瓮城城墙覆盖模型或全屏复原层。
5. 使用 `loc-ar-editor.html` 对照点云摆放模型位置。
6. 保留 debug 面板，便于现场测试识别是否成功。

MVP 可以接受的简化：

- 历史街景模型可以先用低精度占位资产表达，不要求最终考据精度。
- 信息牌可以用 Three.js 平面、CSS2D 标签或简化 3D 卡片实现。
- 瓮城模块可以使用覆盖式模型或全屏叠景，不做真实深度遮挡。
- 体验顺序不固定，只要识别到对应空间即可触发对应内容。

## 测试策略

由于开发者不可能频繁前往阊门现场，测试必须拆分为离线开发、本地传感器测试、临时地图测试和现场校准四层。

### 1. 离线测试内容与遮罩

先实现 `AR Dev Mode`，允许不依赖 Immersal 定位，直接通过 URL 参数或调试面板手动切换内容模块。

示例：

- `loc-ar.html?debugContent=walkway-panels`
- `loc-ar.html?debugContent=portal-song`
- `loc-ar.html?debugContent=portal-mingqing`
- `loc-ar.html?debugContent=battlement-barbican`

离线模式用于测试：

- 漂浮介绍牌是否可读、是否遮挡画面。
- 悬眼 portal 是否只在方形开口内显示历史世界。
- 低模 3D 建筑和背景图是否有足够空间层次。
- 瓮城覆盖层是否能完整覆盖现实画面。
- 手机性能是否稳定。

悬眼遮罩不必一开始依赖真实阊门。可以先使用一张悬眼照片或一个虚拟方形洞口来测试 stencil / clipping / aperture 效果。

### 2. 本地测试陀螺仪与视差

陀螺仪和相机姿态不需要在阊门现场测试。可以在宿舍、教室或任意室外空间用手机打开调试模式，检查：

- 左右转动手机时，历史世界是否像固定在远处，而不是贴在屏幕上。
- 上下抬手机时，洞口远景是否保持合理透视。
- 手机贴近或远离模拟洞口时，portal 大小和远景视差是否自然。
- 横竖屏切换、权限弹窗、传感器初始化是否稳定。
- 站着不动时画面是否明显抖动或漂移。

建议在 debug 面板中显示：

- 当前内容模块。
- 当前 map ID。
- 是否拿到 gyro / device orientation。
- yaw / pitch / roll 或 quaternion。
- 当前定位模式：debug、REST、SDK。

### 3. 临时地图测试识别流程

在正式去阊门前，可以在教室墙面、走廊、宿舍门口等可重复到达的位置创建临时 Immersal map，用于验证“识别 map 后切换内容”的流程。

临时地图不用于最终展示，只用于确认：

- Immersal map 识别是否能触发对应内容模块。
- 多 map 模式下是否会误切换。
- 地图锁定和确认帧机制是否稳定。
- `arAnchors.js` 的内容映射是否正确。

### 4. 现场校准

到阊门现场时，不应从零开发视觉效果，而应只做采样和校准。

每个悬眼最低需要记录：

- 对应 Immersal map ID。
- 悬眼入口宽高、出口宽高、墙体厚度的粗略估计。
- 一张带参照物的照片，例如把手机或手掌放在洞口旁边。
- 识别成功所需时间。
- 手机从哪些角度容易识别失败。
- portal 开口是否与真实洞口远端对齐。

垛口最低需要记录：

- 对应 Immersal map ID。
- 用户站立或举手机的推荐位置。
- 覆盖层触发是否过早或过晚。
- 瓮城复原层是否能遮住主要现实景物。

现场目标是调参，不是写功能。

## 后续完整版本方向

在 MVP 成功后，可以继续扩展：

- 替换为高精度朝代街景复原模型。
- 为介绍牌加入语音讲解或 AI 向导文本。
- 给不同朝代传送窗加入环境音、人物活动、船只移动等轻动画。
- 增加拍照打卡功能，让用户保存“悬眼中的历史街景”。
- 增强空间遮挡，例如用深度估计、手动遮罩或场景几何体模拟城墙遮挡。
- 将主站已有时间轴、河流叙事和路线推荐内容与 AR 模块打通。

## 给 AI 的实现提示

在继续实现时，请不要把该产品理解成普通网页介绍页。它应当基于当前 AR 原型开发，重点是空间识别后的内容切换。

优先阅读以下文件：

- `js/ar/arAnchors.js`
- `js/ar/arScene.js`
- `js/ar/arRenderer.js`
- `js/ar/arPlacementEditor.js`
- `src/pages/ArPage.jsx`

实现时应保持现有架构：

- Immersal 负责识别真实空间。
- `arScene.js` 负责启动、定位、地图锁定和状态控制。
- `arRenderer.js` 负责把当前 map 对应的 AR 内容渲染到相机画面上。
- `arAnchors.js` 负责声明不同地图和锚点内容。
- `loc-ar-editor.html` 用于调试和摆放锚点。

不要把体验写成固定线性流程。正确逻辑是：识别到什么空间，就显示什么历史内容。
